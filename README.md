# Лабораторная работа № 3. «Продвинутая работа с Git. Перебазирование, управление конфигурацией.»

## Цель и задачи работы.

Цель работы: Закрепить на практике работу с удаленными репозиториями, освоить процесс перебазирования, научиться управлять конфигурацией Git и работать с тегами.

К концу практики учащийся должен суметь:

- Форкать репозиторий и клонировать его на локальную машину.

- Настраивать локальную конфигурацию Git для конкретного репозитория.

- Работать с несколькими удалёнными репозиториями (origin и upstream).

- Выполнять перебазирование и разрешать конфликты, возникающие в его процессе.

- Публиковать изменения с принудительной заменой истории.

- Создавать аннотированные теги и публиковать их на удалённом репозитории.

## Разбалловка и требования.

Минимальный балл - 3, максимальный - 6.

Выполняется в индивидуальном порядке. Примерное время выполнения - 90 минут.

## Ход работы

Вы - разработчик, желающий внести вклад в open-source игровой фреймворк. Преподаватель - мейнтейнер этого проекта. Вам предстоит форкнуть репозиторий, реализовать новую функциональность в отдельной ветке, синхронизировать свою работу с актуальным состоянием проекта, подготовить релиз и аккуратно завершить работу.

Команды для использования в работе: git clone, git config, git remote, git branch, git switch/checkout, git add, git commit, git rebase, git tag, git fetch, git push.

### 1. Клонирование репозитория и конфигурация.

1.1. Перейдите на страницу репозитория преподавателя в Github и нажмите кнопку “Fork” в правом верхнем углу экрана. Дождитесь завершения операции. В вашем аккаунте появится копия репозитория.

1.2. На странице репозитория СВОЕГО ФОРКА скопируйте URL. На вашем компьютере, перейдите в папку, в которой будет ваш репозиторий. Откройте там терминал. Через терминал, склонируйте себе репозиторий: git clone <URL>.

Теперь у вас есть локальная копия репозитория.

1.3. Установите локальные настройки имени пользователя и email для этого конкретного репозитория (это важно для отслеживания авторства коммитов). 

Проверить, что настройки применились, можно командой git config --list. Вы должны увидеть установленные вами значения в конце списка. Обратите внимание: эти настройки переопределяют глобальные только для данного репозитория.

1.4. По умолчанию, удаленный репозиторий с именем “origin” указывает на ваш форк. Теперь нужно добавить связь с исходным репозиторием, чтобы получать из него обновления. Это репозиторий, который вы форкали. Измените свой удалённый репозиторий, дав удаленному репозиторию имя “upstream” (общепринятая практика): git remote add upstream <ссылка\_на\_репо\_препода>.

Проверьте список всех удаленных репозиториев: git remote -v. У вас должно быть два: “origin” (ваш форк) и “upstream” (репозиторий преподавателя).

### 2. Перебазирование.

2.1. Изучите историю коммитов в ветке “main” через git log --graph. Обратите внимание, что в репозитории уже есть несколько коммитов от мейнтейнера. Создайте новый файл documentation.md и задокументируйте в нём историю коммитов - как менялся проект (в общих словах) - и для чего он предназначался.

2.2. Перейдите на два коммита назад от текущего состояния “main” - вы должны оказаться на коммите 80e34f6.

Переходить на несколько коммитов назад можно через git checkout HEAD\~N, где N - число коммитов, на которые вы хотите откатиться.

Находясь на нужном коммите, создайте и переключитесь на новую ветку с именем “feature”. 

2.3. Заметьте, что разработчик делал на данном коммите и после него. Представьте, что вы тестируете альтернативные варианты переменных для геймплея.

Откройте проект в Godot Engine (версия .NET). Сначала, поиграйте в него, чтобы посмотреть, как работает логика.

Откройте файл сцены Bat.tscn. В инспекторе, измените значение параметров, отвечающих за амплитуду передвижения летучих мышей. Сохраните сцену. Протестируйте новый геймплей, запустив проект. Добавьте изменённый файл в индекс и создайте коммит.

2.4. Далее, выберите один файл из сцен: Player.tscn, Zombie.tscn, Rock.tscn, Field.tscn. Откройте его, найдите в Инспекторе кастомные параметры, и измените в них значения. В зависимости от выбранной вами сцены, эти параметры могут быть либо высотой прыжка, уроном от пули, здоровьем, или скоростью передвижения.

Сохраните сцену. Протестируйте новый геймплей, запустив проект. Добавьте изменённый файл в индекс и создайте коммит.

2.5. Откройте ещё один файл из вышеупомянутых, но на этот раз другой. В нём, также в инспекторе, измените значение некоего параметра. Сохраните сцену. Протестируйте новый геймплей, запустив проект. Добавьте изменённый файл в индекс и создайте коммит.

Всего у вас должно было получиться три новых коммита на ветке “feature”, где каждый коммит изменяет ОДИН файл сцены .tscn.

2.6. Переключитесь на ветку “main”. Изучите историю коммитов. Обратите внимание, что main ушёл вперёд от точки, в которой вы создали feature. В частности, коммит 227b0f8 содержит правки параметров геймплея, внесённые мейнтейнером уже после того, как вы начали работу в “feature”. Ваша ветка теперь отстаёт от “main” на несколько коммитов. Переключитесь обратно на “feature”.

2.7. Теперь вам нужно переместить вашу ветку “feature” на вершину актуального состояния “main”. Это сделает историю проекта линейной и чистой. Убедитесь, что вы находитесь в ветке “feature”. Выполните перебазирование. Если конфликтов не возникло, rebase пройдет успешно. Ваш коммит теперь будет находиться поверх актуального состояния “main”.

Если в процессе возникнет конфликт (а он, скорее всего, возникнет, т.к. мейнтейнер в коммите 227b0f8 тоже редактировал параметры в вышеупомянутых сценах), Git остановит процесс. Откройте конфликтующий файл, удалите разделители <<<<<<<, =======, >>>>>>>, осмысленно объединив изменения. Затем:

> git add <конфликтующий\_файл>

> git rebase --continue

Повторяйте до завершения rebase.

### 3. Публикация результатов и маркировка.

3.1. Так как вы переписали историю, обычный push не сработает. Нужно отправить изменения с принудительной заменой (--force-with-lease — это безопасная альтернатива --force).

3.2. Ваша работа завершена и готова к "релизу". Создайте аннотированный тег для текущего состояния. Отправьте созданный тег на удаленный репозиторий origin.

3.2. Ваша работа завершена и готова к "релизу". Создайте аннотированный тег для текущего состояния. Отправьте созданный тег на удаленный репозиторий `origin`.
